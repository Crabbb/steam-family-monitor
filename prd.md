# Product Requirements Document (PRD): Steam Monitor Web Service

## 1. Введение
Сервис предназначен для автоматического отслеживания покупок или добавлений новых игр в библиотеки Steam указанных пользователей. В случае обнаружения новой игры сервис формирует детальное информационное сообщение и отправляет его в заданный Telegram-чат. Продукт заменяет существующий жестко закодированный n8n-пайплайн, предоставляя удобный веб-интерфейс для настройки и управления.

## 2. Глоссарий
* **Пользователь (User)** — человек, профиль Steam которого отслеживается системой.
* **Администратор** — человек, использующий веб-интерфейс сервиса для настройки мониторинга.

## 3. Целевая аудитория
Геймеры и группы друзей, которые хотят быть в курсе новых приобретений друг друга в Steam, чтобы вовремя предлагать совместную игру.

## 4. Функциональные требования (Functional Requirements)

### 4.1. Управление системными настройками (Web UI)
Администратор должен иметь возможность задать через веб-интерфейс следующие глобальные настройки:
* `Steam API Key` — ключ для доступа к интерфейсам Steam.
* `Telegram Bot Token` — токен бота, от имени которого будут приходить уведомления.
* `Telegram Chat ID` — ID чата/группы, куда бот будет отправлять уведомления.

### 4.2. Управление списком пользователей (Web UI)
Интерфейс должен позволять управлять списком отслеживаемых профилей:
* Добавление нового пользователя (Поля: `Имя` или `Никнейм`, `Steam ID`).
* Редактирование существующих пользователей.
* Удаление пользователей.

### 4.3. Тестовая отправка сообщения
* В списке пользователей для каждого отслеживаемого аккаунта должна быть кнопка «Отправить тестовое сообщение».
* При нажатии бот должен отправить в указанный Telegram-чат тестовое уведомление от имени этого пользователя с использованием **случайной игры** из базы Steam.
* Тестовое сообщение должно иметь в начале явный дисклеймер (например, `[ТЕСТ]`).

### 4.4. Мониторинг библиотеки Steam (Background Job)
* Сервис должен периодически опрашивать Steam API для каждого из заведенных пользователей. Интервал проверки должен настраиваться через веб-интерфейс (значение по умолчанию — 1 раз в 15 минут).
* При первом запуске сервис собирает текущий список игр каждого пользователя и **не отправляет** уведомления, а только сохраняет начальное состояние (защита от спама).
* При последующих проверках сервис сравнивает текущий список игр с предыдущим:
  * Если найдены новые ID (которых раньше не было в локальной базе) — инициируется процесс отправки уведомления.
  * Сервис получает детали об игре из магазина Steam (русский язык: `cc=ru&l=russian`).
  * База (состояние пользователя) обновляется новыми ID игр.
* **Независимость проверок:** Ошибка при проверке одного пользователя (например, скрыт профиль) не должна прерывать проверку остальных.

### 4.5. Шаблон сообщения Telegram
Сервис должен форматировать HTML-сообщение в точности так же, как это делалось в n8n скрипте:

#### Логика форматирования:
1. Цена: "Бесплатно / Неизвестно" либо точная цена магазина. Если есть возможность, выводится цена в РФ (рубли) и цена в КЗ (тенге, конвертированные в рубли для удобства). Если есть скидка — отображается процент.
2. Режимы (категории): Выводятся только важные теги, если они есть у игры: "Для одного игрока", "Для нескольких игроков", "Кооперативная игра", "PvP", "Кроссплатформенная игра".
3. Metacritic: Если есть — выводится кликабельная ссылка с рейтингом `Оценка/100`.
4. Ссылка на ProtonDB для проверки совместимости с Linux / Steam Deck.
5. Индикатор семейной библиотеки: Если есть информация о том, доступна игра в семейной библиотеке или нет — это статус выводится в сообщении.

**Пример (HTML разметка):**
```html
🚨 <b>Новая игра у {Имя пользователя}!</b>

🎮 <b><a href="https://store.steampowered.com/app/{AppID}">{Название_игры}</a></b>

💰 <b>Цена:</b> {Цена_РФ} / {Цена_КЗ_в_рублях_с_указанием_КЗ}
🎯 <b>Режимы:</b> {Режимы_или_"Не указано"}
👨‍👩‍👦 <b>Семейная библиотека:</b> {Доступно/Недоступно}
⭐ <b>Metacritic:</b> <a href="{Ссылка}">{Score}/100</a>
🐧 <b>ProtonDB:</b> <a href="https://www.protondb.com/app/{AppID}">Проверить совместимость</a>

📝 <i>{Описание_игры_(short_description)}</i>
```

### 4.6. История сообщений (Web UI)
* Веб-интерфейс должен содержать раздел "История логов / История сообщений".
* В истории отображаются все отправленные сервисом уведомления (включая тестовые) с датой, именем владельца и названием игры.

## 5. Нефункциональные требования (Non-Functional Requirements)

### 5.1 Работоспособность и Надежность
* Система должна обрабатывать ошибки API безопасно (например, Steam API rate limits, недоступность серверов Steam или Telegram).
* В случае ошибки получения данных об игре из магазина (отсутствует `gameData`), должно отправляться fall-back сообщение: `🎮 <b>{Имя пользователя}</b> купил игру (ID: {AppID}), но деталей в магазине нет.`

### 5.2 Производительность
* Обращения к Steam API должны быть легковесными, чтобы не вызывать блокировку по IP (учитывать паузы между запросами, если пользователей станет много).

### 5.3 Безопасность
* Сервис будет размещаться локально на Raspberry Pi владельца, поэтому дополнительная авторизация в веб-панели и скрытие токенов не требуются (подразумевается, что доступ имеет только сам пользователь в локальной сети).

### 5.4 Технологические ограничения
* На данный момент "Никакой дополнительный функционал не нужен".
* Сервис должен иметь модульную архитектуру для возможного дальнейшего расширения.

## 6. Деплой
* В конце разработки сервис должен быть развернут на локальном Raspberry Pi в соответствии с воркфлоу `deploy_to_pi.md`.
